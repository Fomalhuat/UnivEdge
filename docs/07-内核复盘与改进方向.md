| 测试 | 我们的表现 | 暴露的问题 |
|---|---|---|
| 4A 推导线 | 抓到一个真 bug（漏角向 Christoffel），锚点对照有效 | 流程有效，无系统性问题 |

## 1. 缺口分析（经用户讨论修正后的最终结论）

### 缺口 B（唯一硬缺口，P0）：自洽性验证 ≠ 正确性验证；测试设计本身要被审查

**两个层面：**

**B1 约定/实现层错误漏网**：4B 的"负 m 对称关系 ratio=1.00000000 全 PASS"是用**同一个有 bug 的 Ylm 函数**验证的——自洽但错了（正确关系 ΦS_{l,-m} = (−1)^m ΦS_{l,m}）。内部一致性检查全部通过也可能整体错误。

**B2 测试设计本身有盲区**（源自 h 测试教训）：用户原话——"当时认为已经把所有测试都做过了，但是没想到测试本身也有错误，最后还是靠其他 AI 重新研究这个问题才发现的"。h 测试"变化不大"实为只改演化 h 不改源表 h：测试者以为在测一个因素，实际漏了另一个关键因素。

**结论**：不仅产物要被审查，**审查标准/测试设计本身也要被审查**。且测试流程复杂时，研究者未必了解全部细节 → **测试设计必须双层审查：研究者确认方向 + AI（怀疑派评估器）审查细节**。

### 缺口 D（软性规则，P1）：主动请求锚点

用户给 ret 数据时，若 agent 先问"你知道 Φ_res 的收敛值是多少吗？"，能更早发现偏差（用户其实有真值 −1.0498e-3）。这是"锚点原则"的主动形式：**锚点缺失时，请求锚点优先于给出结论**。但研究者没有义务必须提供——软性规则，不强制。

### 缺口 A（降级，P2 建议性）：物理量定义

用户修正：论文语境里"1/ρ"就是 Φ_s 的标准记号，附录 B 给了 THZ 坐标转换，代入即得四阶——**不存在歧义**。内核不可能（也不应该）预知所有研究语境，研究者把情况说明白是合理分工。→ 契约中"物理量定义"改为**建议性字段**：语境已明确可省略，语境不明确时建议公式级描述。

### 缺口 C（降级，P2 报告附注）：近似等级

用户修正：忠实报告收敛结果就是正确行为；研究者预期不符时提出进一步要求，属正常协作。→ 不强加"近似充分性检查"，只在报告模板中**附注收敛趋势**（档差衰减指数、是否已饱和），供研究者判断。

## 5. 后续修订（2026-08-14 追加）

> 07 定稿后，v0.4/v0.3 又经历几轮实质性修订。本节补齐变更史，保证 07 作为完整变更记录。

### 5.1 测试计划分层（han 确认）

- **问题**：测试计划"列出测试 + 每个测试覆盖的因素/通道"直接展示给研究者会太长；研究者未必了解测试方法细节。
- **方案**：测试计划分两层——【概要层 · 研究者看】测试项 + 判据（可判定）+ 目的 + 怀疑派评估器审查结论回填；【明细层 · 评估器审查用】因素/通道映射明细（契约附录或 run/ 独立文件，L3 按需）。
- **落地**：METHODOLOGY §1.2 测试计划段 + §5.5 输入分层与结论回传；VERIFICATION RC-05 同步。

### 5.2 教训库类型化 → 根因基 B1–B4（han 提出，元思想固化）

- **问题**：具体教训是无限集，全部记载不现实；应提炼**类型特征**，AI 只需思考方向。
- **演进**：6 类（约定歧义/验证盲区/工具陷阱/数值边界/文献冲突/过程迷失）→ 经"线性独立基"检验，**过程迷失是果非因**（其他基未被拦截的累积后果），剔除 → 最终 4 根因基：
  - **B1 无依据断言**（捏造/幻觉）
  - **B2 语义歧义**（定义/约定/参照不唯一）
  - **B3 工具/方法误用**（有效域/约定陷阱）
  - **B4 验证失效**（meta 层，拦截器）
- **元思想固化**（METHODOLOGY §1.5）：领域内核固化的是从例子抽象出的**线性独立的根因基**，不是例子本身；新基须检验独立性（是否为已有基的线性组合）。
- **落地**：knowledge/review-lessons.md 重构为基层（B1–B4，L1 常驻 ~20 行）+ 例子层（L3 按需）；§1.1 增加"检索教训（每次必做）"。

### 5.3 全内核泛化检查（根因基思想的延伸）

- **问题**：内核文件中存在领域术语残留（张量/指标/缩并、球谐/度规、具体数值、人名 han）。
- **原则**：**规则主体必须领域无关，领域内容只出现在例子层**。
- **落地**：SC-02/03/04"自由指标平衡/缩并/张量类型"→"数学结构自洽（若适用：张量指标平衡、矩阵维度、级数阶次）"；CC-01 例子泛化；VERIFICATION §5 JSON 示例用中性占位；runtime-contract/README 的"han"→"用户"；METHODOLOGY §5.5 h 测试实例移入 docs/07 引用。

### 5.4 写作约定元规则（han 确认）

- METHODOLOGY 写作约定新增：**本文终态 = 结构收敛**——新增规则前先问"是否已有根因基的实例"；结构性修改应收敛，"完成"= 不再需要新机制。
- 判断完成的判据：连续若干轮 vertical slice 无新增规则需求，只有 knowledge/ 例子增长。

### 5.5 实战验收（P0/P1，2026-08-14）

- **P0 knowledge/**：conventions.md（约定注册表）+ review-lessons.md（根因基）+ README 导航建立——CC-01 与 §1.5 的前置基础设施。
- **P1 ret−THZ4阶singular 验收**：完整走 v0.4 新流程（测试计划双层、CC-01、NC-06、RC-04、RC-05、已知参照值软性字段）——Φ_res(L=30)=−1.049686e-3 vs 真值 −1.0498e-3 偏差 0.01%，档差指数 p≈3.96，与有效源方法互证 0.0086%。
- **实战发现（B3-3 教训）**：远程权威实现 thz_c_lm 内区切平面近似带 ~1.2e-5 系统误差——"整体验证通过"≠"子组件精确"，继承上游组件须做有效域边界测试。NC-06/RC-04 的价值包括防"权威源"的近似。
- **结论**：v0.4/v0.3 新机制经实战验收有效，**无新增规则需求**——机制层零修改，仅 knowledge/ 例子层增长（符合设计）。

### 5.6 run/ 定位修订：产物存储可插拔（2026-08-15，han 提出）

- **问题**：原定义把 run/ 当"会话/检查点/日志"（docs/03、docs/05）——那是设计完整 agent（含运行时）时的概念；harness 定位下会话/检查点/日志已委托宿主，run/ 实际只承担**子任务审计产物**（契约/报告/数据/脚本）。
- **han 观点**：run/ 对 harness 是**可插拔的插件**——换宿主场景时不应绑定目录结构，否则 harness 越来越大。
- **方案**：接口化——本体只定义产物**格式**（契约模板/报告结构/数据规范），存储**位置**由宿主提供（METHODOLOGY 新增 §1.6）；run/ 降级为"当前 WorkBuddy 宿主的实现"，非本体内置目录。
- **落地**：METHODOLOGY §1.6（产物存储定义）+ 全部 run/ 引用改为"产物存储"；docs/03 注释、docs/05 组件归属矩阵（R4 会话检查点归宿主、日志存储归宿主）；AGENTS.md/README 同步。
