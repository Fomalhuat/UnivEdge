# 物理科研 Agent 构建计划 · Step 1：文献调研与设计蓝图

> 日期：2026-08-11 ｜ 状态：草稿 ｜ 目标读者：本项目成员
> 定位：这是整个项目的第一份工程文档，回答"我们要造什么、参考了什么、为什么这样设计"。

---

## 0. 核心命题

- **Agent 本质上是方法论的工程化。** 一个领域特化 agent 之所以优秀，是因为它把该领域优秀研究者的行为模式固化为可执行的框架。OpenAI 所说的 **harness engineering**，指的是大模型之外的全部支撑：环境、工具、反馈回路、控制系统、知识结构——也就是"马鞍"。模型是马，harness 决定它能稳定地跑多快、跑多远。
- **本项目目标**：把"优秀物理研究者的行为模式"抽象为可执行规范，再通过 harness（工作流状态机 + 验证工具栈 + 纪律强制层）固化为一个**面向天体物理/物理研究的科研 agent**。
- **路线**：文献调研（本步）→ 方法论规格 → 验证协议 → 最小实现 → 评测集。每步都产出可评审的文档，不跳过验证。

## 1. 参考案例盘点

### 1.1 DeepMath（同济大学团队）—— 数学创造力 agent
仓库：https://github.com/DeepMathLLM/DeepMath

**两个连续工作：**

| 工作 | 内容 | 关键结论 |
|---|---|---|
| DeepMath-Creative（arXiv:2505.08744） | 首个"数学创造力"基准：代数/几何/分析的构造性问题 | 最强模型（O3-mini）在**本科级**创造题仅 ~70%；复杂度上升后性能崩塌；开放式问题几乎沉默。即"重组记忆强、真创造弱" |
| DeepMath-Generator | 两 agent 架构生成微分几何研究问题 | 产出 **665 个专家验证的研究级问题**，覆盖 200 个知识点 |

**Generator 工作流**（从 README 流程图还原）：

```
知识点输入 (200 个)
      │
      ▼
┌─────────────────┐   生成问题   ┌─────────────────┐
│  Generator LLM  │ ───────────► │  Evaluator LLM  │
│  (创意角色)      │              │  (质量把关)      │
└─────────────────┘              └─────────────────┘
      ▲                                  │
      │       未通过（迭代重试，          │ 通过
      │        至 MAX_ATTEMPTS）         ▼
      └────────────────────────── 保存 .tex（合格问题）
                                          │
                         5 题/知识点 → 下一知识点（×200）
                                          │
                                          ▼
                              665 个专家验证的研究问题
```

**可迁移的设计要点：**
1. **创造与批判解耦**：Generator 与 Evaluator 是独立角色、独立 prompt（仓库中 `generator_prompt.md` / `evaluator_prompt.md` 分离）。让"提出"和"挑错"互相独立，避免自说自话。
2. **简单而鲁棒的循环**：生成 → 评估 → 迭代，显式终止条件（PASS 或 MAX_ATTEMPTS），无复杂编排。
3. **专家验证作为最终裁判**：人类位于验证链末端——凡是"被当作正确的"结论，都经过独立检验。这正是我们项目要继承的第一原则。
4. **任务空间切片**：按"知识点"切分（200 点 × 5 题），可并行、可追踪、可评估覆盖率。

> ⚠️ 同名混淆提示：另有 Intel Labs 的 "DeepMath"（轻量数学推理 agent：Python 沙箱执行 + GRPO 强化训练，smolagents 实现，HF blog 发布）。两者无关，本项目参考的是同济 DeepMath 的 agent 工作流思想。

### 1.2 OpenAI：Harness Engineering（2026-02，Ryan Lopopolo）
原文：https://openai.com/zh-Hans-CN/index/harness-engineering/

文章背景是"纯 Codex、零人工编码"开发百万行软件产品，但其中的 harness 原则可完整迁移到科学 agent：

1. **记录系统（System of Record）**：知识必须落在 agent 可访问、版本化的 artifact 中；**"运行时不在上下文里的知识 = 不存在"**。→ 科研 agent 的文献、主张、实验记录都必须是可读文件，而不是埋在聊天记录里。
2. **地图而非手册（渐进式披露）**：一份 ~100 行的 AGENTS.md 只做"目录"，指向深层文档；巨型说明书会挤占上下文、迅速腐烂、难以核实。→ 方法论手册必须分层。
3. **机械强制执行不变量，而非微观管理**：用 linter / 结构测试把"品味"编码成规则，在边界处强制，在局部放权。→ 物理领域的对应物就是"物理合理性检查器"（§2.3）。
4. **反馈回路**：智能体自审 + 智能体互审（"Ralph Wiggum 循环"），直到所有评审满意。→ 科研 agent 需要内置评审角色。
5. **熵管理（垃圾回收）**：定期后台任务清理漂移与陈旧文档；人类品味持续注入。→ 科研 agent 的知识库同样会"腐烂"，需要维护机制。
6. **瓶颈在环境设计**："构建软件仍然需要纪律，但纪律更多体现在支撑结构上，而不是代码上。"——对科研 agent：纪律体现在 harness 上，而不是祈祷模型更聪明。

### 1.3 Google AI Co-Scientist（2025-02，Gemini 2.0）
博客：https://research.google/blog/accelerating-scientific-breakthroughs-with-an-ai-co-scientist/

- 多 agent 协作：**Generation / Reflection / Ranking / Evolution / Proximity / Meta-review + Supervisor**，官方明确说灵感来自科学方法本身；
- **Elo 锦标赛**式假设排序与自我改进 + test-time compute 扩展；显式模拟"科学争论"；
- 在急性髓系白血病药物重定位、肝纤维化、耐药性基因转移（帝国理工，AI 数天复现人类数年路径）等案例中获得实验验证；
- 定位为**专家在环**的协作工具，而非全自动替代；
- 官方承认局限：文献综述质量、事实核查、自动评估都仍需人工兜底。→ 再次佐证：**验证必须外置、独立于生成**。

### 1.4 Sakana AI Scientist（arXiv:2408.06292）
- 首个**全自动端到端**科研管线：想法生成 → 文献新颖性检索 → 实验代码编写/执行 → 图表 → 论文 → 自动同行评审，开放式迭代；
- 每篇论文成本 ~$15；评审 agent 的评分与人类评审相关性较高；
- **已知缺陷（重要教训）**：幻觉风险（以"代码评审 agent"缓解）、"人气偏差"（偏爱高引论文）、部分论文结论经不起推敲。
- 结论：**端到端全自动为时尚早**；每个环节必须有独立校验，且评测（而非论文产出）才是衡量真实能力的标尺。

### 1.5 ScienceAgentBench（ICLR 2025，arXiv:2410.05080）
- 从 44 篇同行评审论文提取 **102 个任务**（4 学科），9 位领域专家校验；
- 最好 agent 独立解决率仅 **32.4%**，加专家知识 34.3%，o1-preview + 自我调试 42.2%；
- 核心呼吁：**在宣称端到端自动化之前，先对工作流中的单个任务做严格评测**。
- → 直接支持我们的"一步一步来"路线：先跑通并评测最小闭环，再谈完整科研循环。

## 2. 数学 vs 物理：对 agent 设计的根本差异（核心分析）

| 维度 | 数学研究 | 物理研究 |
|---|---|---|
| **验证方式** | 形式化证明（Lean/Coq）或同行专家，可接近确定 | **无单一形式化裁判**：分析检验 + 数值检验 + 数据统计检验三层，互相补充 |
| **结论性质** | 命题真/假（公理系统内） | 模型 + 有效域 + 不确定性（近似真理，可被新数据推翻） |
| **研究起点** | 定义、公理、猜想 | 观测异常、数据、理论张力、"如果……会怎样" |
| **关键技能** | 构造反例、证明策略、结构洞察 | 建模艺术（自由度/对称性/尺度/理想化）、量级估计、拟合与统计推断、误差分析 |
| **LLM 典型错误** | 证明步骤缺陷、伪定理 | 幻觉常数/公式、**单位错误**、非物理结果（负光度、超光速）、忽略系统误差、错误引用 |
| **可机械化的"不变量"** | 类型检查、逻辑检查、证明器 | 维度分析、单位检查、守恒律、极限情形、量级检验（Fermi 估计） |

### 2.1 推论一：物理 agent 没有"单一验证器"，必须有"三层验证栈"

数学 agent 的验证可以委托给证明器（或专家）；物理没有 Lean 式裁判。因此：

- **分析检验**：维度分析、单位一致性、守恒律、对称性、极限情形（如 $h\to0$、$c\to\infty$、$\nu\to0$）；
- **数值检验**：收敛性（分辨率/步长）、可复现性、与独立数值方法的交叉验证；
- **数据检验**：似然/χ²、贝叶斯因子、系统误差盘点、模型比较（BIC/AIC）、预测 vs 观测。

每层独立给出 **通过 / 不通过 / 需人工** 三态，任何一层"不通过"都不能进入"结论"状态。

### 2.2 推论二：物理结论天生携带不确定性 → 强制产物结构

每个研究产物必须绑定**假设清单 + 有效域 + 误差预算**。这不是建议，而是 harness 里必须强制的数据结构（否则 agent 会像常见 AI 一样把未验证结论当正确结论使用）。

### 2.3 推论三：物理 LLM 的多数错误"便宜可查" → 物理合理性 linter

单位错、量级错、守恒违背、非物理值——这些不需要深度推理即可机械拦截，对应 OpenAI 文章里的 linter 思路：**把"品味"写成可执行规则**。一个 physics linter（单位检查 + 量级估计 + 守恒 + 极限 + 正定性等）能拦掉大量幻觉，这是物理 harness 相对通用 agent 的最大杠杆。

## 3. 方法论提炼：优秀物理研究者的行为模式（草案，Step 2 细化为可执行规范）

1. **问题导向**：从 anomaly / 理论张力 / 数据驱动出发，不凭空堆砌课题；
2. **建模艺术**：显式选择自由度、对称性、尺度，记录理想化假设及代价；
3. **先量级后精确**：任何计算前先做 Fermi 估计与维度分析，建立直觉；
4. **多维验证**：分析 + 数值 + 数据三路并进，交叉印证；
5. **证伪意识**：主动寻找反例、矛盾证据、替代解释；
6. **文献锚定**：结论与已有结果交叉验证，来源可追溯；
7. **诚实的不确定性**：结论带误差、有效域、后续验证建议，明确"claimed / verified"状态。

## 4. 物理 Agent Harness 蓝图（骨架）

```
┌─────────────────────────────────────────────────────────┐
│              人类科学家（专家在环，最终裁判）              │
├─────────────────────────────────────────────────────────┤
│ L4 反馈层   评审 agent · 自我评审循环 · 熵管理(doc-gardening) │
├─────────────────────────────────────────────────────────┤
│ L3 纪律层   physics linter · 假设清单强制 · 对抗审查(反方)  │
├─────────────────────────────────────────────────────────┤
│ L1 工作流层 物理方法状态机：提出→建模→推导/计算→预言→检验→   │
│            结论(带误差)→迭代；产物状态标签: claimed/derived/ │
│            analytically-checked/numerically-checked/     │
│            data-supported/rejected                        │
├─────────────────────────────────────────────────────────┤
│ L2 验证工具层 SymPy(符号) · astropy(单位/坐标) · 量级估计器  │
│             数值收敛检查 · 统计检验(χ²/Bayes) · 拟合管线     │
├─────────────────────────────────────────────────────────┤
│ L0 知识层   文献库(arXiv) · 主张注册表 · 模型注册表 · 假设账本 │
│             数据溯源 —— 全部为版本化可读文件(渐进式披露)      │
└─────────────────────────────────────────────────────────┘
  领域工具生态：numpy/scipy · astropy · emcee/MCMC · CIGALE · MESA · arXiv API
```

设计要点：
- **状态机是骨架，不是靠提示词**：产物状态（claimed → verified → rejected）由 harness 强制流转，LLM 无权自行声称"已验证"；
- **工具栈物理特化**：单位/量级/极限检查是物理 agent 的"类型系统"；
- **专家在环**：参考 co-scientist，人类在关键检查点介入，不追求全自动（ScienceAgentBench 的数据说明全自动仍不现实）。

## 5. 初步技术选型与实现路径

- **框架**：优先复用成熟 agent 框架（smolagents / LangGraph / OpenHands），把"物理方法论"实现为 workflow + tools + guards，不重复造 LLM 调度轮子；
- **最小闭环（vertical slice）建议**：选一个小而真实的物理任务，例如——"给定一篇论文的物理结论，自动执行 单位检查 → 维度分析 → 量级估计 → 极限情形 四连验证"，跑通 提出→验证 的最小回路；
- **评测**：仿照 ScienceAgentBench 构建小型物理任务集（单位/维度/量级/复现/反例），作为迭代回归测试。
