# UnivEdge 设计审查 · 运行时契约与组件归属（05）

> 日期：2026-08-11 ｜ 状态：草稿
> 触发：han 观察到"UnivEdge 目前更像一个大的 skill"，通用 agent（opencode/Reasonix/Pi）中的上下文管理、会话、权限、沙箱等运行时组件尚未纳入。

---

## 0. 结论

- han 的观察**成立且方向正确**：UnivEdge 目前的 90% 是知识/方法论层（本质就是一个"超级技能"）。
- 运行时组件（上下文管理、会话/检查点、执行沙箱、权限门、模型路由、日志）**确实需要，但不是"重新实现"**——它们是通用能力，与物理领域无关，重复造轮子成本高且难做好（Reasonix 为前缀缓存做了一整套 append-only 设计，Anthropic 在上下文重置上花了大功夫）。
- 正确做法是**分层 + 运行时契约**：
  1. **领域层（UnivEdge 本体）**：方法论、验证协议、任务契约、产物状态机、知识库、技能、工具定义——**以及"运行时契约"（对宿主的要求清单）**；
  2. **通用运行时层（宿主或薄运行时）**：上下文管理、会话/检查点、沙箱、权限门、模型路由、日志——委托宿主，缺失时用薄运行时补齐；
  3. **适配层（tools/）**：具体执行环境接入（本地沙箱、远程 HPC、符号引擎）。

---

## 1. 为什么"像一个大的 skill"其实是正确的

- 领域特化 agent 的价值 = 领域方法论，方法论本质上就是一个"超级技能"（技能 = 方法论 + 工具的知识包）；
- 但 UnivEdge 比普通 skill 多出三层：**可移植仓库结构**（可整体迁移）、**产物状态机与验证管线**（claimed→verified→rejected）、**运行时契约**（声明宿主需提供什么）；
- 普通 skill 是"宿主里的一段指令"；UnivEdge 是"可迁移的 agent 配置 + 知识 + 工具 + 契约"。

## 2. 组件归属矩阵（核心）

| 组件 | 通用 agent 的做法 | 归属 | 理由 |
|---|---|---|---|
| 上下文管理（压缩/重置/steering） | Reasonix append-only；Anthropic context reset | **委托宿主 + 契约** | 通用能力；交接工件格式由 UnivEdge 定义 |
| 会话 / 检查点 / 分支 | Pi JSONL 树；Reasonix checkpoint rewind | **委托宿主 + 契约** | 通用能力；检查点粒度由 UnivEdge 定义（产物存储可插拔，见 METHODOLOGY §1.6，非本体内置） |
| 执行沙箱 / 多语言 | opencode bash；Reasonix bwrap/Seatbelt | **委托宿主 + 适配层（tools/）** | tools/ 已有占位 |
| 权限门 | opencode a/A/d；Reasonix gateApprover | **委托宿主 + 契约** | 副作用分级由 UnivEdge 定义 |
| 模型路由 / 成本 | Reasonix flash→pro 自动升级 | **委托宿主 + config/** | config/ 已有占位 |
| 日志 / 可观测性 | 各家均有 | **委托宿主 + 契约** | 日志格式由 UnivEdge 定义；存储归宿主 |
| 事件循环 / agent 循环 | 各家核心 | **委托宿主** | 领域无关 |
| **方法论 / 验证协议 / 任务契约 / 产物状态机 / 知识 / 技能 / 工具定义** | （领域特有，通用 agent 不做） | **UnivEdge 本体** | 核心价值，全部已有 |
| **运行时契约（接口清单）** | （无先例，各家隐含） | **UnivEdge 本体（新增）** | 可移植性的关键 |

## 3. 运行时契约（Runtime Contract）——新增 R7

**定义**：UnivEdge 声明其运行所需宿主能力的接口清单，是"可移植性"从口号落到工程的关键。

- 形式：`config/runtime-contract.md`（草案已建，见仓库）；
- 条目草案：
  1. **R1 执行环境**：多语言执行（Python/C++/Fortran，至少 Python）+ 远程执行（ssh/SLURM，可选）；
  2. **R2 权限门**：副作用分级（L0 只读 / L1 本地写 / L2 高危：HPC 提交·网络），L0 可自动放行，L1/L2 需 han 批准；
  3. **R3 上下文管理**：支持压缩与重置（以交接工件开始新回合）；交接工件格式 = 产物状态 + 上下文地图 + 任务契约；
  4. **R4 会话与检查点**：会话持久化/恢复；检查点可标记、可回退（科研实验版本管理）——实现归宿主，产物存储为宿主提供的可插拔位置（METHODOLOGY §1.6）；
  5. **R5 模型路由**：任务类型/难度 → 模型（推理强 / 便宜快速），config 可配；
  6. **R6 可观测性**：结构化日志、token 用量、工具调用记录，agent 可读。

---

## 4. 决策：本轮只定义契约，不实现运行时

- **理由**：YAGNI + 可移植性优先。vertical slice（Step 4A）跑通之前，先明确"宿主要提供什么"；跑通后按真实缺口决定是否补薄运行时；
- **薄运行时**（可选、低优先级）：宿主产物存储下的最小脚本集——交接工件生成、检查点标记、权限门 CLI；
- 评估宿主满足度：当前宿主（WorkBuddy）对 R1（Python 沙箱）、R2（执行确认）、R4（会话）满足；R3/R5/R6 需按宿主能力配置或降级。
