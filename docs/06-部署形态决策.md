# UnivEdge 设计决策 · 部署形态：skill 外壳 vs agent 外壳（06）

> 日期：2026-08-11 ｜ 状态：决策（han 确认后生效）
> 问题：UnivEdge 作为领域层，最终是"像 skill 一样注入宿主使用"，还是"借鉴开源通用 agent 的运行时包装成独立 agent"？

---

## 0. 结论

**这是伪二选一。** 两种形态本质是同一个架构（领域层注入宿主）在不同宿主上的投影。正确策略是**分阶段**：

- **Phase 1（现在）**：skill 外壳，注入现有宿主（WorkBuddy），以最小成本验证方法论；
- **Phase 2（触发时）**：agent 外壳——借用开源通用 agent（opencode / Reasonix / Pi 或自建薄运行时）作为宿主，UnivEdge 领域层原样注入；
- **关键**：无论哪种外壳，**UnivEdge 本体（docs/knowledge/skills/tools/契约）一行不改**——这就是运行时契约（docs/05）存在的意义：外壳只是适配层。

---

## 1. 拆解：为什么是伪二选一

- **skill 形态** = 领域层 + 薄适配层 + 现成宿主（WorkBuddy 等）；
- **agent 形态** = 领域层 + 厚适配层 + 运行时宿主（opencode/Reasonix 等开源运行时，或自建）；
- 两者的领域层完全相同，区别只在"适配层厚度"和"宿主是谁"。

**"借鉴开源通用 agent 的其他部分"的正解**：不是把 opencode 的运行时抄进 UnivEdge（那是重复造轮子），而是**把开源运行时当作宿主**，UnivEdge 以领域层注入它。这实际上把两种形态统一了——都是"UnivEdge 领域层注入某个宿主"。

---

## 2. Phase 1：skill 外壳（推荐起步）

- **做法**：把 UnivEdge 包装为"领域 skill 包"注入宿主。在 WorkBuddy 中 = SKILL.md（入口/导航）+ docs（方法论）+ knowledge（注册表）+ skills（子技能）+ tools（工具脚本）+ config（运行时契约映射）；
- **优点**：零运行时开发成本；宿主提供上下文管理/权限/会话；迭代快（方法论改进 = 改文档）；复用已验证路径——han 的 xAct skill 与 PRD77 复现就是在该形态下完成的；
- **代价**：领域特有的交互（任务契约确认、锚点复核、权限分级、检查点回退）依赖宿主能力，宿主不支持则降级。

---

## 3. Phase 2：agent 外壳（触发时再升级）

- **做法**：选一个开源运行时作宿主（opencode/Crush、Reasonix、Pi 皆 MIT/开源），UnivEdge 领域层 + 厚适配层注入；或自建薄运行时（run/ 脚本集 + 简单 CLI）；
- **优点**：完全可控；任务契约/权限门/检查点可做到最优；可独立部署、团队共用；
- **代价**：开发与维护成本（运行时 = 对模型缺陷的补偿，模型升级要重审——Anthropic 原则）。

**升级触发条件（满足其一即考虑）：**
1. 宿主上下文管理不满足"交接工件"需求（压缩/重置行为不可控）；
2. 权限门分级不够（L2 高危操作如 HPC 提交无法细粒度批准）；
3. 需要脱离当前平台部署（服务器、团队共用、长期运行任务）；
4. 方法论验证成熟，值得"产品化"。

---

## 4. 架构保障：如何让两阶段无痛切换

- 领域层对外只依赖**运行时契约（R1–R6）**，不依赖任何宿主的具体机制；
- skill 外壳与 agent 外壳都是"契约 → 宿主能力"的映射器，各自独立实现；
- 因此：**先以 skill 形态跑通 vertical slice，验证的是方法论；方法论成立后，加壳是纯工程**，不涉及领域层返工。

---

## 5. 对 Step 2 及后续的影响

- METHODOLOGY.md 内容与部署形态**解耦**：方法论规范只谈"做什么、怎么验证"，不谈"在哪个宿主里跑"；
- vertical slice（Step 4A/4B）默认在 skill 外壳下进行；
- 若触发条件出现，新建 `deploy/`（agent 外壳）目录，复用 docs/knowledge/skills/tools。

---

## 6. 一句话总结

> **以 skill 形态出生，以 agent 形态成长**——出生只带方法论（轻），成长靠借宿主（不重造运行时），切换时领域层不动（契约兜底）。
