# 08. 内核维护工作流（监护人角色）

> 日期：2026-08-16（自 METHODOLOGY §9 迁移）｜状态：活文档（随每次评审迭代）
> 定位：判断"内核是否需要优化"的标准流程——监护者（对内核最了解的会话）执行；
> 适用于跨会话任务结果的评审（其他会话执行任务 → 本流程评审 → 决定机制层是否修订）。
> 来源：2026-08-16 换模型回归实战 + han 确认的跨会话工作模式。
> 归属说明：运维流程，非执行 agent 行为规范——故不驻留 METHODOLOGY（必要性原则），
> 作为独立文档随评审迭代；METHODOLOGY 的写作约定元规则（终态=结构收敛）与之呼应。

## 1. 评审输入（交结果时应含 5 项）

1. 任务描述 + 任务契约（若执行会话走了契约）；
2. 产物路径（报告/数据/脚本）；
3. 验证记录（锚点对照、交叉验证结果）；
4. **遇到的坑**（失败最暴露内核问题，即使任务失败也须提供）；
5. 执行会话的工作目录路径（用于查证执行痕迹）。

## 2. 评审方法（3 步，怀疑派立场）

1. **对照锚点核验**：结果 vs knowledge/benchmarks.md（B1-B7），偏差超阈值即未命中，声称无效；
2. **查执行痕迹**：确认真跑证据（中间值序列/脚本/时间线/环境细节），防"声称复现"——尤其注意收敛序列等中间值不可能从任何允许读文件抄到的判据；
3. **问题归因**：失败/偏差先归因到 B1-B4 根因基（执行问题）或新基（内核问题），不直接判"内核要改"。

## 3. 判据（何时需要优化机制层）

| 结论 | 条件 |
|---|---|
| 不需要优化 | 结果命中锚点，暴露问题能归入现有 B1-B4 基 → 只需知识层增长（教训/约定/基准加条目） |
| **需要优化**（4 种） | ① 新根因基（无法由 B1-B4 线性组合）；② 现有规则被证无效/误导（检查项形同虚设）；③ 流程死锁（契约太重导致任务无法推进）；④ 知识库缺失直接导致任务失败 |

## 4. 评审节奏（长任务）

- **评审点 = 每个"有独立可验证产物的子任务"完成时**（非按时间——无锚点的节点不设评审点）；
- **阶段评审轻量**：只查本阶段产物命中锚点 + 方向未跑偏（claimed → verified 升级）；
- **完整评审**（12 项 checklist，见 run/benchmark/review.md）留到任务收尾；
- **原理**：锚点原则的时间延伸——阶段产物先 claimed，评审通过升 verified，成为下一阶段锚点；防"过程迷失"（17 天无效循环教训，B4 拦截器在时间维度的落地）。

## 6. skill / 工具引入检查

引入外部 skill 或工具到 `skills/` 时，除功能与许可审查外，强制检查：

1. **自包含性（零悬空引用）**：裁剪（排除大文件/二进制/私有内容）后，必须 Grep 所有保留文件中对被排除路径的引用（如 `lectures/`、`templates/*.nb`、`references/xAct/`），逐处改写为"增强资源三件套"：①声明不随仓库版打包；②给出获取途径（探测顺序：本 skill 目录 → 宿主 user 级 → 公开仓库 → 官方源）；③给出降级路径（自包含速查，找不到不卡住）；
2. **泛化性**：去本机路径/凭据/绝对路径，改为探测 + 询问；
3. **同源校验**：与完整版共用的 SKILL.md / 索引文件用 md5 双校验，确保知识版与发布版一致；
4. **许可**：第三方内容须确认可再分发（GPL / 官网公开渠道），保留许可文本（如 xAct 的 gpl.txt）。

> 实例：xact-assistant 2026-08-16 入库时漏了第 1 条——`lectures/` 等大文件被排除后，SKILL.md 与索引仍保留对其引用（悬空）。本次修复并建立 `xact-assistant-release` 公开仓库作为完整版分发源，知识版仅留"资源可用性"解析指引。
