## 0. 结论摘要（三段式）

**直接结论**：han 的猜测方向正确——Claude 的审查频率确实远低于"每步都审"，且 Anthropic 自己的
演化方向就是**主动删审查**（V1 per-sprint 评估 → V2 运行结束单次通过，评估器成本占比 8.3%）。
但归因需要修正：UnivEdge 的性价比问题**不在触发判据**（v0.12 引入的四信号已与 Claude 同构）。
v1.2 经两轮评审后的归因为：① **毕业机制空转**（所有工作类型永远处于"默认审"状态——唯一退出路径
从未被数据喂过）；② **记录不承载判据**（INDEX 无"档位"字段，"是否过审"当前不可审计）；
③ ~~单次审查太贵~~（v1.2 作废——评估器自 10-10 起只审 C/H 项；机械项的真实问题是**无人执行**
的覆盖缺口，属质量而非成本）。

**任务性质差异的诚实保留**：Claude 审代码（漏一个 bug 的代价是改代码，oracle 是廉价的测试）；
UnivEdge 审物理结论（漏一个约定错误/参照污染可能代价数月下游计算，oracle 是昂贵的锚点对照）。
因此 UnivEdge 的审查成本**合理地应高于** Claude 的 coding harness——但不能高到"每次全量、永不毕业"。
合理目标不是"和 Claude 一样少"，而是"**每一次审查都值回其下游代价**"。

**修改意见（v1.2 修订后排序，详见 §4）**：
R2 毕业机制数据化（唯一退出路径）→ R3 档位可审计性（先补"档位"记录字段，须 han 裁决）→
R1 覆盖缺口修复（**质量杠杆，非降本杠杆**；R1b 推迟到真实任务数据后）→
R4 嗅探通道按证据退役 → R5 模型升级触发承重重估（与信号④合流）。

## 2. 一手来源核实：Claude 的审查机制实况

来源：Anthropic Engineering, *Harness design for long-running application development*
（Prithvi Rajasekaran, Labs），2026-10-13 重新抓取原文全文核实（非二手转述）。

### 2.1 V1 harness（Opus 4.5）：per-sprint 全量评估

- 三 agent 架构：planner / generator / evaluator（GAN 启发，生成与评判分离）；
- **每个 sprint 前协商 sprint contract**（生成者与评估者迭代至一致），判据含**硬阈值**，
  "if any one fell below it, the sprint failed"；
- evaluator **每个 sprint 都评分**（用 Playwright MCP 实际操作运行中的应用再打分）；
  粒度实例：Sprint 3 一个 sprint 27 条判据；
- 成本：6h / **$200**（solo 对照：20min / $9——全 harness 贵 20 倍以上，但质量差异"immediately apparent"）。

### 2.2 V2 harness（Opus 4.6）：删除 sprint 构造，评估器降为单次通过

原文明确的简化路径："I started by removing the sprint construct entirely...
**I moved the evaluator to a single pass at the end of the run rather than grading per sprint.**"

实测成本分布（原文表格，DAW 构建任务）：

| 阶段 | 时长 | 成本 |
|---|---|---|
| Planner | 4.7 min | $0.46 |
| Build R1 | 2h 7min | $71.08 |
| **QA R1** | 8.8 min | **$3.24** |
| Build R2 | 1h 2min | $36.89 |
| **QA R2** | 6.8 min | **$3.09** |
| Build R3 | 10.9 min | $5.88 |
| **QA R3** | 9.6 min | **$4.06** |
| **合计** | 3h 50min | **$124.70** |

**评估器（QA）合计 $10.39 ≈ 总成本 8.3%、总时长 ~11%；4 小时运行仅 3 轮 QA。**

### 2.3 判据与元原则（原文直引）

能力边界判据（审查是否值得的**唯一**判据）：

> "Tasks that used to need the evaluator's check to be implemented coherently were now often within
> what the generator handled well on its own, and **for tasks within that boundary, the evaluator
> became unnecessary overhead**. But for the parts of the build that were still at the edge of the
> generator's capabilities, the evaluator continued to give real lift."

> "The practical implication is that **the evaluator is not a fixed yes-or-no decision. It is worth
> the cost when the task sits beyond what the current model does reliably solo.**"

承重组件元原则（对应 UnivEdge 已有"模型升级重审 harness"惯例）：

> "**Every component in a harness encodes an assumption about what the model can't do on its own**,
> and those assumptions are worth stress testing, both because they may be incorrect, and because
> **they can quickly go stale as models improve**."

怀疑派调优方向被原文验证（评估器默认不可信，必须调优）：

> "Out of the box, Claude is a poor QA agent. In early runs, I watched it identify legitimate issues,
> then talk itself into deciding they weren't a big deal and approve the work anyway."

其调优法 = 读评估器日志 → 找与人类判断的分歧 → 改 prompt → 迭代数轮——与 UnivEdge §5.3
怀疑派调优 + 分歧日志机制同构。

### 2.4 低频 ≠ 低价值

即使 V2 只剩 3 轮 QA，每轮仍抓到真问题（核心功能 display-only、录音 stub、裁剪/分割未实现等）。
**评估器被保留不是惯性，而是持续有产出**——成本-收益的度量应看"命中率 × 下游代价"，
不是审查次数本身。

## 3. 归因分析：UnivEdge 的成本高在哪里

### 3.1 三层归因表

| 层 | Claude 的做法 | UnivEdge 现状（2026-10-13 核实） | 诊断 |
|---|---|---|---|
| **触发判据** | 能力边界（任务属性，非时间点） | §1.7 四信号（能力边界/下游代价/生命周期/变更事件；v0.12 引入，现行 v0.13 未变），源自 docs/09 对同一原文 + OpenAI 来源的调研 | ✅ **已同构**——判据不背锅 |
| **单次审查成本**（v1.2 重写） | 机械验证走测试/编译（零 token）；evaluator 只做语义判断 | 评估器 prompt **自 2026-10-10（commit `1637f70`）起只列 C/H 项**（`univedge-reviewer.ts` L435-437：RC-01~07、CC-01、NC-04/05/06）——**机械项已无 token 成本可省**；但 9 个机械项（V+V*）**仅 1 个有 verifier**（NC-01），其余 8 个**无人执行** | ⚠️ **v1.0/v1.1"每次全量 LLM 评估"作废**：成本侧差距比文中所言小；真实问题是**覆盖缺口**（该查的没查），不是"查得太贵"。剩余成本杠杆 = 14 个 H 项的**形式层拆分**（未被本轮评审推翻，但缺真实任务成本数据支撑优先级） |
| **动态收缩** | 模型升级即重审承重组件（4.5→4.6 直接删 per-sprint 评估） | `knowledge/work-types.md` 全部 8 类工作状态 = capability，**审查次数/实质发现计数全为 0**（2026-10-10 建表至今）；漏审登记表为空 | ❌ **毕业机制从未触发**——没有计数就没有毕业，没有毕业就永远 capability（永远"默认审"） |

### 3.2 "频繁"感受的机制性来源

1. **毕业机制空转**（主因）：v0.12 设计的退出路径（20 次零实质发现 → regression 自动门 → 不调评估器）
   依赖计数数据，而计数从未开始。所有工作类型被锁定在 capability 态 = 全部默认审。
2. ~~单次审查过宽（V/V* 进 prompt）~~ **（v1.2 作废此条）**：该描述是 v0.11 时代的旧状态
   （抄自 docs/09 差距表，未对照现行实现），2026-10-10 起 prompt 已只含 C/H 项。
   "审查太多"的感受在当前数据下**无法归因于单次成本**——40 次审查全部发生在装置维护期
   （无一次真实物理任务），唯一成本样本为 10-10 的 6 次 ≈ 24.8M tokens ≈ 3.97 元。
3. **双通道叠加（过渡期现象，v1.1 修正表述）**：§1.7 观察期内自动嗅探通道与宣告通道并行。
   **2026-10-12 han 已裁决"自动审查收窄"**：装置（dsh-adapter）改动不再自动触发审查
   （远程 commit `552b63c`，含六项检查 + 逃生门 `UNIVEDGE_REVIEW_APPARATUS_AUTO=1`）——
   叠加效应已部分消除；嗅探对其余写入仍在过渡期承担兜底职责
   （此为本体已知的过渡态，非设计缺陷）。

### 3.3 合理溢价的边界（诚实保留）

不能拿 Claude 的 8% 当 UnivEdge 的目标，两个不对称：

| 不对称 | Claude（coding harness） | UnivEdge（物理科研） |
|---|---|---|
| 漏审代价 | 改代码（小时级） | 下游数月计算污染（实例：rewrite3d 方程缺几何项 1.5 天才暴露） |
| oracle 成本 | 测试/编译（廉价、确定性） | 锚点对照（本身昂贵，部分 H 项不可约地需要 LLM/人判断） |
| 信号②命中率 | 低（单次构建下游有限） | 高（产物常成为后续锚点/触发全链重算） |

→ 频率与单次深度高于 Claude **有正当理由**；不正当的部分是 §3.2 的机制性浪费
（v1.2 修正后：毕业机制空转 + 档位不可审计；原"单次过宽"一条已作废）。

## 4. 修改意见（交开发 agent 评审）

> 以下每条含：落点（改哪个文件哪节）、内容、前置条件、预期收益、风险。
> R1/R2 是结构性杠杆；R3/R4 是执行核查；R5 是机制补全。

### R1 覆盖缺口修复（v1.2 重新定位：**质量杠杆，非降本杠杆**）

- **v1.2 定位修正依据**（开发 agent 修正一，本人已独立复现全部命令）：评估器 prompt 自 2026-10-10
  起只列 C/H 项 → 机械项无 token 成本可省，"降本"定位作废。真实问题是：**9 个机械检查项中 8 个
  处于"无人执行"状态**——既不在评估器 prompt（§5.1 限定 C/H，执行已遵守），也无 verifier 实现。
  即 §5.1 的"机械/语义分流"只完成了一半：机械项被移出了评估器，却没有落到脚本执行者上，
  **形成了检查真空**。
- **落点**：`tools/verifiers/checks/`（补实现）+ 审查流程中 verifier 的调用位（宿主侧）。
- **内容**：
  1. ~~R1a 条款声明 + 执行核查~~ **已完成**（开发 agent 核查 + 本人复现：条款早已存在 §5.1，执行已遵守）；
  2. R1b 补 8 个 verifier（SC-01/02/03/04/06、NC-02、NC-03、PC-01）——**采纳开发 agent 建议：
     推迟到真实物理任务数据之后**（见 §9 问题 5）。届时按"哪个机械项对当前任务最关键"排序
     （例：rp=12 FEM 验证链最相关的是 NC-02 收敛阶、NC-01 已覆盖锚点表）；
  3. R1c H 项形式层拆分 + 报告结构约定——**保留为候选成本杠杆**（本轮评审未推翻），
     但优先级同样待真实任务成本数据（当前 40 次审查全在维护期，无分解依据）。
- **预期收益（修正后）**：堵住"机械项无人执行"的检查真空——这是**漏检风险**（质量），
  收益形态是"该查的有人查"，不是"审查变便宜"。
- **风险**：低；但注意 verifier 上线后应有"谁调用、何时调用"的流程位，否则补了实现仍无人执行。

### R2 毕业机制数据化：让 work-types.md 真正转起来（唯一退出路径）

- **落点**：`knowledge/work-types.md` §2 计数列 + 审查产物模板（要求每轮审查报告显式给出"实质发现数（按口径）"）+ `run/review/INDEX.md`（登记时同步更新计数）。
- **内容**：
  1. 从即日起每轮审查结束时按既定口径计数（实质发现 = §5.6 核验 ✅ 且影响结论/数据/误差预算/状态标签）；
  2. 审查报告模板增加一行"实质发现计数：N（明细：...）"——否则计数依赖事后人工回填，必然再次空转；
  3. 每月（或每 20 次同类审查）复核一次状态表，触发首批 capability → regression 毕业；
  4. 漏审登记表（§3）同步启用——双向指标（漏审率 + 过审率）缺一不可（docs/09 O4）。
- **前置条件**：无（口径已在 METHODOLOGY §1.7 与 work-types.md §1 定义）。
- **预期收益**：1–2 个月数据后，稳定类型毕业为脚本自动门 → 审查频率**结构性**下降；这是"默认审"唯一的退出机制。
- **风险**：中低。主要风险是计数口径执行漂移（"实质发现"判宽判窄）→ 缓解：每月复核时抽查 2-3 条计数记录与原始审查报告对照。
- **注意（原文警示）**：某类工作"审查屡屡无功"时，先怀疑**审查配置**（清单/判据是否还对准该类失败模式），再考虑毕业——"0% pass rate across many trials is most often a signal of a broken task, not an incapable agent"。毕业前须确认审查配置本身有效。

### R3 档位纪律核查 → **R3' 档位可审计性**（v1.2 修订：先补记录字段，须 han 裁决）

- **v1.2 修订依据**（开发 agent §4，本人已复现）：INDEX 字段 = 时间/主会话/评估者/结论/触发通道/
  关联任务/报告路径——**无"档位"字段** → 判据存在（§1.7 轻量/全量）但记录不承载 → **当前不可审计**。
  间接线索：报告字符数 577~11,059（多数 5,000~8,000），不足以定论。
- **落点**：`run/review/INDEX.md` 表结构 + 审查落盘代码（dsh-adapter）。
- **内容**：给审查记录补"档位"字段（轻量/全量），补字段后即可执行原 R3 的审计。
  **注意**：加字段属元层扩张，按 `VERIFICATION §3.4.1 #5` 须 **han 裁决**后方可实施。
- **预期收益**：使"轻量档是否被全量化"从不可判定变为可查表判定。
- **风险**：低（字段追加，不改既有列）；风险在流程侧——落盘代码需同步填该字段，否则新字段全空。

### R4 嗅探通道按证据退役（§1.7 既定计划收尾；v1.1 更新）

- **落点**：宿主侧（dsh-adapter review triggers）+ METHODOLOGY §1.7 观察期条款。
- **v1.1 进展注记**：2026-10-12 的"自动审查收窄"裁决（装置改动不再自动触发）是观察期内的
  **第一次按证据收窄**——方向与 R4 一致，可视为 R4 的部分前置执行；但其范围仅限装置改动，
  嗅探通道对其余写入仍在运行，**退役决策本身尚未做出**。
- **内容**：观察期数据评估——宣告覆盖率 / 嗅探边际价值（嗅探独有触发的审查中实质发现数）/ 误触发率。
